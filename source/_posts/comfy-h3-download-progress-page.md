## 结论先给

要给一个要好几天的大文件下载做「实时进度页」，最省事的不是上框架，是**本地起一个只读 Python 状态服务器 + 一个每 2 秒自动刷新的 HTML 页面**。页面内嵌数据、用 `<meta http-equiv="refresh">` 自己刷新，**完全不依赖 fetch**——这是绕开 CORS 的关键。

但这个看似简单的方案里埋着三个坑，我全踩了一遍：

1. **`file://` 页面对 `localhost` 的 `fetch` 被 CORS 拦死**——`file://` 的 origin 是 `null`，直接请求被浏览器拒绝，服务器根本收不到。
2. **`_poll()` 里缺一句 `global _state`**——Python 函数内赋值创建了局部变量，模块级的 `_state` 永远是空的，进度条显示 0%。
3. **多次「重启」服务器，旧进程没死透，三个进程争抢同一个端口**——请求随机落到旧代码进程上，行为时好时坏。

下面按「怎么想到的、怎么发现的、怎么修的」讲清楚，每一条都是实测数据，不是猜的。

---

## 一、背景：下载要跑几天，怎么让用户实时看到进度

我给 ComfyUI 配 MiniMax H3 视频生成工作流，需要下载约 50GB 的模型。之前一篇博客记过：国内直连大模型仓库慢，我写了个自愈续传脚本 `ensure_h3_models.sh` 挂在 cron 上慢慢爬。脚本把下载进度写进 `h3_download.log`。

这个下载要跑好几天，用户问了一句话：

> 「可以做一个可视化的页面吗？我想看到实时的下载进度」

需求很明确：别光看日志，要一个能自己动、一眼看到进度的页面。

我的方案：**一个 Python 状态服务器 + 一个自刷新 HTML 页面**。

- 服务器每 1 秒采样一次各模型文件的**真实大小**（`os.path.getsize`），算出速率、进度、剩余时间，存进内存状态。
- 页面读状态渲染成卡片 + 进度条 + 日志尾部，用 `<meta http-equiv="refresh" content="2">` 每 2 秒整页重载。

先看这个设计为什么刻意**不用 fetch**，这是后面那个坑的伏笔。

---

## 二、坑 1：file:// 页面的 fetch 被 CORS 拦死

### 怎么想到的

一开始我没把「数据」和「页面」分开。第一版页面打算用 JS `fetch('http://127.0.0.1:8123/progress')` 拉 JSON，再自己渲染。为了验证，我写了个 `fetchtest.html`：

```html
<script>
fetch('http://127.0.0.1:8123/progress')
  .then(r => r.json())
  .then(d => { /* 渲染 */ })
  .catch(e => { document.getElementById('status').textContent = 'FETCH FAIL: ' + e.message; });
</script>
```

在浏览器里用 `file://` 打开这个页面，然后看服务器日志——结果服务器**一个请求都没收到**。这就是证据：不是页面渲染问题，是**请求根本没发出来**。

### 根因

`file://` 页面所在的 origin 是 `null`（不是 `http://127.0.0.1:8123`），浏览器把这次跨源 `fetch` 直接拦掉了。就算服务器设了 `Access-Control-Allow-Origin: *` 也没用——**对 `file://` origin，`*` 也救不了**，因为浏览器的 CORS 检查对 `null` origin 的处理更严格。

我确认这个判断的方式是反向验证：服务器记录了「最近收到过哪些请求的来源」，结果**只有我自己用 `curl` 发的请求，一个来自浏览器页面的都没有**。`file://` 页面的 fetch 到 localhost，是被浏览器拒的，不是网络不通。

### 修复

不跟 CORS 死磕，直接换架构：**服务器同时输出 JSON 和 HTML**，HTML 里内嵌最新数据，页面靠 `<meta http-equiv="refresh" content="2">` 整页自动刷新。这样浏览器每次重新加载都是从 `http://127.0.0.1:8123/` 直接拿完整 HTML——**同源，没有 fetch，没有 CORS**。

```html
<meta http-equiv="refresh" content="2">
```

数据在服务器端渲染进 HTML，浏览器只是「每 2 秒重新请求一次页面」。这是绕开跨源限制最朴素也最稳的办法。

## 三、坑 2：_poll() 缺一句 global，进度永远是 0

### 怎么想到的

服务器改好后，`/` 返回 200、页面能渲染了，但**所有进度条都显示 0.0%**，而且状态里 `files` 一直是空数组。第一反应是「`_ticker` 线程没跑起来」——查了 stdout 没异常，查了线程逻辑也没问题。

卡了一阵才反应过来：这个「空」很反常。**`_poll()` 直接手动调用，返回的也是空**——那问题不在线程调度，在函数本身。

### 根因

看代码：

```python
_state = {"updated": 0, "files": [], "rate": {}, "log_tail": []}   # 模块级

def _poll():
    # 注意：这里没有 global _state ！
    _state = {"updated": now, "files": files, "rate": rates, "log_tail": tail}  # 局部变量！
```

Python 里**函数内对变量赋值，默认创建的是局部变量**。`_poll()` 里 `_state = {...}` 这一行，因为没写 `global _state`，创建的是**函数作用域里的局部 `_state`**，函数一返回就被丢弃；模块级的 `_state` 永远停留在初始的 `{"files": []}`。

所以不是「没数据」，是**数据填到了局部变量里，模块级那个始终是空的**。`/progress` 一直返回 `files: []`，页面自然全是 0%。

这是一个经典的 Python 作用域 bug，藏得很深——因为它**不报错**。`_ticker` 里的 `except: pass` 还会吞掉一切异常，让它「看起来正常但就是不更新」。

### 修复

加一行声明：

```python
def _poll():
    global _state   # ← 就这一行
    ...
```

重启后立即看到正确数据：5 个文件，qwen3vl 文本编码器 84%、ref2va DiT 24%、video/audio VAE 和 LoRA 已完成。**一行 `global`，数据从「永远空」变成「全对」。**

### 教训

Python 的作用域规则在**模块级状态 + 后台线程更新**这个模式里特别容易咬人。以后凡是「函数里要写模块级变量」，第一件事就是检查有没有 `global`。而且这个 bug 还有个帮凶——`except: pass` 把异常全吞了，让故障「隐形」。排查时先去掉 `except: pass`，让异常暴露出来，比对着空数据猜快得多。

## 四、坑 3：三次「重启」留下三个进程，争抢同一端口

### 怎么想到的

改完作用域 bug 重启服务器，页面还是时好时坏：有时候 `/` 返回 200，有时候 `/progress` 返回一个**只有 55 字节**的响应（正常该是几百字节的 JSON）。这种「一会儿好一会儿坏」最误导人。

### 根因

用 `netstat` 查 8123 端口，结果**有三个 python 进程都在监听**（PID 5696、8760、8832）。

原因是我前面修 bug 时反复「重启服务器」，但每次只是 `Start-Process` 起新实例，**旧进程没被杀干净**。于是：

- 三个进程都绑到 8123（Windows 上 SO_REUSEADDR 允许这种抢注，或者它们用不同 socket 参数绑定成功）；
- 新请求**随机落到其中一个进程**；
- 落到旧代码进程的请求，走的是旧逻辑——返回 404 或旧格式 JSON。

这就是为什么行为不稳定：**不是代码错了，是请求被分发到了不同版本的进程**。旧进程 27104 我以为 kill 了，实际还活着；后来新起的 3568、10956、19724 一个个叠加。

### 修复

把监听 8123 的进程**全部杀掉**，确认端口完全释放（`netstat` 无 LISTENING），再启动**一个**干净实例。这次先验证「只有一个监听者」，再测 `/` 和 `/progress`，两个都 200、格式正确，才算完。

### 教训

**「重启」不等于「旧进程退干净」**。Windows 下 `Start-Process` 起后台 Python 进程，父 shell 退出后子进程还在；你 kill 的可能是 pid 文件里记的旧 pid，实际进程早换了。排查「服务行为不稳定」时，**先数监听同一端口的进程数**，别一上来就怀疑代码。

## 五、最后交付的东西

页面做好后，用户直接在浏览器打开 `http://127.0.0.1:8123/` 就能看，每 2 秒自动刷新：

- **顶部 4 张卡片**：已完成文件数、总下载量、当前速率（平滑 30 秒）、预计剩余时间
- **每个文件一张卡**：进度条 + 百分比 + 实时速率 + 剩余量，完成后变绿
- **底部日志**：最近 8 条下载日志

服务器是**只读、无副作用**的（只 `os.path.getsize` + 读日志），不碰下载进程。同时提供 `/progress` JSON API，脚本也能消费。

实现要点就三条，都很便宜：

1. **状态放内存**，`_ticker` 线程每秒采样文件大小；
2. **HTML 服务端渲染**，`<meta http-equiv="refresh">` 自刷新，绕开 CORS；
3. **只读**，不干扰下载本身。

## 六、通用教训

这三个坑其实各自能带走一个通用经验：

**1. `file://` + `fetch(localhost)` = 死路。**
想给本地服务做页面，要么页面本身也从 `http://` 提供（同源），要么别用 fetch。服务端渲染 + meta refresh 是最省心的绕法。别花时间调 CORS 头——对 `file://` origin，调了也没用。

**2. Python「函数改模块级变量」要 `global`，且 `except: pass` 会让它隐形。**
模块级状态 + 后台线程是常见组合，`global` 漏写不报错，只表现为「数据永远空」。配合 `except: pass`，你看到的是「安静地什么都不更新」，而不是异常。排查顺序：去掉 `except: pass` 暴露异常 → 检查作用域声明 → 再怀疑线程。

**3. 服务行为时好时坏，先数监听端口的进程数。**
「重启」在 Windows 后台进程场景下常常不干净。行为不稳定时，`netstat` 看同一个端口几个 LISTENING，比猜代码快得多，也准得多。

下载类任务尤其值得做进度可视化——因为它**慢到以天计**，用户需要知道「到底在不在动、还要多久」，而不是对着一个纹丝不动的日志干等。

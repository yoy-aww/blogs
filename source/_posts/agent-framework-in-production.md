## 先说结论

很多人以为"公司用 Agent 框架"意味着"业务代码里直接调 LLM 让它干活"——**这不是公司常态**。

一句话：

> **生产系统的管道用确定性代码，LLM 只出现在"理解"类步骤里，prompt 版本化管理。**

Agent 框架（Hermes、Claude Code、LangGraph 这些）在生产里更多是**辅助工具**，不是主干。就算公司真的用 Agent，"Skill"的内容最终也会固化进服务代码里——变成 prompt 模板、RAG 知识库、规则配置，而不是运行时让 LLM 去读一份 SKILL.md。

这篇写的是我最近处理一个真实任务（招聘 PDF 提取入库）时想清楚的事：什么样的活该让 LLM 干、什么样的活必须用代码干、生产形态长什么样。

上一篇 [Function Calling 和 Skill 是什么关系](/2026/10/23/function-calling-vs-skill/) 讲的是概念分层。这篇讲**这些概念在生产里长什么样**。

## 为什么"Agent 直接跑业务"不现实

不是不能跑，是**不值得跑**。三个理由：

**1. 确定性 vs 概率性**

我那个招聘 PDF 提取任务，逻辑很固定：扫目录、提取字段、按 phone 去重入库。用 Python 写 300 行代码，行为 100% 可预期。

让 LLM 按一份 SKILL.md 去做这件事——每次有微小不确定性。某份 PDF 字段顺序怪了点，正则写歪了，或者某一行简历格式特别——它可能就卡住或者搞错。

生产系统的原则是：**能不用 LLM 就不用**。

**2. 成本**

每个 Agent 循环都要消耗 LLM token。处理 21 份 PDF 无所谓，跑 21 万份简历就是 21 万倍的调用费。

LLM 按量计费不是抽象概念，是会出现在月底账单上的具体数字。

**3. 可测试性**

独立项目能跑单元测试、CI/CD、代码审查。"让 Agent 按 SKILL.md 干活"没法写断言——你没法用 `assert` 锁住 LLM 下一次生成的内容。

这三条叠在一起，就是为什么**生产环境几乎不用纯 Agent 模式**。

## 三档现实落地

按"实际生产里谁在干活"分：

| 场景 | 用什么 | 占比 |
|---|---|---|
| 高并发、对外提供 API、有 SLA | 独立微服务（Python FastAPI / Go / Java） | 大多数 |
| 低并发的后台任务（定时跑、几十到几千条数据） | 定时脚本 / 独立小服务 | 不少 |
| 探索性、一次性、个人或小团队工作流 | Agent 框架 + Skill | 快速增长中，但还不是主流 |

绝大多数公司的"Agent 项目"，实际形态是第一档或第二档——**Python/Node 服务，只在某一步调 LLM**。第三档是最近这两年在快速膨胀，但还没成为主流。

## 2026 年的真正主流：混合式

真正在生产跑通的 Agent 项目，架构图大概长这样：

```
Python/Node 微服务
  │  负责确定性管道：扫文件、调外部 API、写数据库、错误重试
  │
  └── 调 LLM 的步骤（用 prompt 模板）
        │  prompt 模板是版本化的代码，进 git，走 code review
        │
        └── 可选：复杂决策分支外挂 Agent 框架
```

关键点：

- **主干是确定性代码**：扫文件、写 DB、调外部 API、做重试——这些都是经典工程，LLM 不掺和
- **LLM 只在"需要理解"的步骤出现**：比如"从简历里提取技能关键词"、"判断这份合同的风险条款"、"总结这段对话的结论"
- **prompt 是代码，进 git**：版本化、code review、回滚、A/B 测试——prompt 不再是"改改看"的随手东西
- **可选外挂 Agent**：确实需要"让 LLM 自己决定下一步"的场景才挂 Agent 框架，不是默认

换句话说：**就算公司"用 Agent"，那个 SKILL.md 最终也会变成 prompt 模板文件、知识库配置，或者硬编码的规则**——而不是让 LLM 在运行时去读一份动态加载的剧本。生产上那一步太贵、太慢、太不可控。

## 什么时候该用 Skill / Agent，什么时候不该

判断标准其实很朴素——**看任务的确定性**：

**该用 Agent / Skill 的：**

- 任务逻辑变化快，写死代码维护成本高于 LLM 调用成本（比如"每周根据新政策调整分类规则"）
- 任务本身就是"人做的事"——审查、分类、写文档、排障、给建议
- 探索阶段，先跑通再考虑工程化
- 输入本身是非结构化的、需要"理解"的（不是"格式转换"）

**不该用、该写代码的：**

- 任务逻辑稳定、输入格式固定、输出可预期
- 高并发、有 SLA 要求
- 需要写断言、跑 CI
- 任务里每一步都是确定性的

## 一个真实案例：招聘 PDF 提取

我最近做的一个任务特别能说明这个边界。

**任务**：把一堆招聘简历 PDF 提取成结构化数据入库（姓名、电话、技能、项目经验等）。

**乍一看是个"AI 任务"**：PDF 内容非结构化，得让 LLM 来"理解"。

**但拆开看其实是个混合任务**：

| 步骤 | 用什么 | 为什么 |
|---|---|---|
| 扫 Downloads 目录、识别 PDF 文件 | Python 代码 | 纯确定性，没必要让 LLM |
| 用 PDF 库提取文本层 | Python 库（pdfplumber 等） | 确定性，有现成库 |
| 提取字段（姓名、电话、邮箱、教育经历） | 正则 + 规则 | 格式固定，正则稳定 |
| 识别技能关键词 | LLM | "Python 经验 3 年" vs "用过 Python" 的语义判断 |
| 按 phone 去重、写入数据库 | Python 代码 | 确定性 |

**字段提取是确定性的，技能关键词提取带理解成分**。所以正确的形态是：**Python 脚本做主干，只在"技能识别"这一步调 LLM**——不是让 LLM 从头到尾处理整份 PDF。

数据量小的时候（几十个文件、手动触发），用 Agent + Skill 跑够了，不值得工程化。数据量大（HR 系统每天几千份简历），就该写独立 Python 服务：`FastAPI + 定时任务 + SQLite/PG`。

**判断标准不是"任务像不像 AI 任务"，而是"任务里哪几步真正需要理解"**。

## 面试可以直接用的一句话

> "我们项目的管道用确定性服务（Python/Node），判断类步骤调 LLM，prompt 版本化管理、进 git、走 code review。Agent 框架只在需要'让 LLM 自己决定下一步'的复杂分支上外挂。Skill 里的方法论最终会固化进服务代码里，不会让 LLM 在运行时读一份动态剧本——生产上那一步太贵、太慢、太不可控。"

这一段回答了面试官关心的三个问题：

1. **怎么保证系统稳定**：主干确定性代码，LLM 只在外围
2. **怎么控制成本**：LLM 只调用必要步骤，不是全流程跑
3. **怎么做质量保障**：prompt 版本化，能 code review，能回滚

## 我自己在做的事，和这个结论一致吗

回头看我现在写的这个博客——它的内容来源就是一个 Hermes 会话里的问答，由 Hermes 这个 Agent 总结成草稿、写到 markdown、跑 `hexo generate`、`git commit`、`git push`。

**这恰好是"该用 Agent 的"那一档**：

- 任务逻辑变化快（每次选题、写作风格都不同）
- 任务本身就是"人做的事"（写文章）
- 探索阶段，先跑通再说
- 输入是非结构化的（几十天的会话记录）

如果我硬要把"博客写作"工程化成一个 Python 服务，每一步都是写死的模板——那做出来的文章读起来就是流水账。这种任务**就应该让 Agent 干**。

所以结论不是我"觉得 Agent 不靠谱"，而是：**Agent 用对地方很强，用错地方是灾难**。判断标准是"这一步任务是不是确定性的"，不是"公司是不是 AI 公司"。
